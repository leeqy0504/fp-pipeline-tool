Web UI 后端架构 — 3 种方案

核心分歧：FastAPI 怎么调用 Pipeline Stage

A

方案 A：直接调用（推荐）

FastAPI 直接 import pipeline 模块，stage.run() 跑在 asyncio 后台线程，WebSocket 推实时日志

方案 A 架构
🌐 浏览器 ←HTTP/WS→ FastAPI → import pipeline.stages.* → run()
所有东西在一个 Python 进程里

Pros

  • 直接调现有 pipeline 模块，零改造
  • manifest 断点续跑直接用
  • 部署最简单，一个进程跑所有
  • WebSocket 日志直通 stage 输出

Cons

  • 长任务（混元 20min 轮询）卡线程
  • 服务挂了 pipeline 也挂
B

方案 B：子进程调用

FastAPI 保持 Web 逻辑，pipeline 通过 run.sh 子进程执行，stdout 捕获后推 WebSocket

方案 B 架构
🌐 浏览器 ←HTTP/WS→ FastAPI → subprocess → ./run.sh stage masks
Pipeline 独立进程，Web 进程只管调度

Pros

  • Web 和 pipeline 进程隔离
  • 完全兼容现有 run.sh 调用方式

Cons

  • 需要解析 stdout 来追踪状态
  • manifest 状态和进程状态要额外同步
  • 部署多一层（PID 管理）
C

方案 C：任务队列

加 Redis + Celery/ARQ，任务入队持久化，Worker 执行，Web 只做前端

方案 C 架构
🌐 浏览器 ←HTTP/WS→ FastAPI → Redis → Celery Worker → stage.run()
经典任务队列，组件多但成熟

Pros

  • 任务持久化，重启不丢
  • 多任务排队天然支持
  • Worker 可独立扩缩

Cons

  • 多引入 Redis + Celery 两个依赖
  • 部署复杂度翻倍
  • 当前单用户场景用不上队列
